# Ошский: остановка ПЧ4, обратный отсчёт и анимация

**Дополнение26.11, локальный уже работает:** пользователь подтвердил ещё
один дефект — в **AUTO при реальном ожидании** не было обратного отсчёта
до запуска и отключения ведомых. Продолжить текущую работу с сохранением
RAM/копий/результатов; добавить раздел3ниже. Не начинать разбор/перенос заново.
Принятая STOP-проверка токов и полей задержек не является проверкой countdown.

Базовые файлы — PLC r3 и HMI r3d. Если текущая работа уже дала более свежую
копию/несохранённый буфер, продолжить её после сохранения, не откатывать
к базовым файлам. На предыдущем шаге пользователь ещё не передавал
c671d12 локальному; теперь сообщил, что локальный работает. Принятый им
commit отдельно не подтверждён. Полевой эпизод: **ручной режим, ПЧ4 уже работал,
регулярно появлялась «Ошибка подготовки режимов ПЧ», ПЧ4 останавливался,
на самом приводе собственного кода аварии не было**.
Токи/задержки/переходы на физической панели уже
[приняты пользователем](../reports/oshsky-physical-hmi-user-check-20261126.md).

Дополнительный Main-кадр:1–3работают35.0Гц,4остановлен0.0Гц при ручном
задании35.0Гц; его Пуск запрещён, под карточкой «Исключён из AUTO».
Это не самостоятельная причина запрета в MANUAL. На кадре журнала активных1,
но точные времена не читаются. Не назначать причину по порядку размытых строк
или по AUTO membership и не считать эти фото новым стендовым regression.

Это одно объединённое поручение. Вначале разобраться с остановкой, затем
выполнить уже подготовленный раздел анимации из
[задания физической HMI](oshsky-r3d-physical-panel-local-20261126.md).
Не терять успешную r3d и не повторять исходную загрузку PLC без новой причины.
Разрешения на автономную работу с копиями и загрузки на идентифицированном
стенде сохраняются; повторного общего подтверждения не спрашивать.

## 1. Локализовать самое первое событие

Прочитать [анализ двух путей останова](../reports/oshsky-mode-stop4-analysis-20261126.md)
и [точную дисковую r3](../reports/oshsky-first-start-r3-readonly-local-20261126.md).
Cloud проверило4 selected-target mode-fail и6 generic-link-drop сценариев
на отдельных actual bytecode predicates generated r3. Это не полный FUN150
и не установленная полевая причина. Сверить actual native r3 перед изменением.

Приоритетная гипотеза: неудача дополнительного FC03 по slave4 обнуляет
M613, затем M713 и manual permit, хотя собственная частота ещё свежая.
После этого очередь может вновь готовить режим, но эта последовательность
в поле пока не записана. Проверить альтернативы: write/readback/stop-check
error, неправильный адресат, старый ответ, owner/очередь/deadline и потеря X4.

Зафиксировать **контекст одного первого сбоя**, до его перезаписи очередью:

- normal poll D300/D301: результат/строка/slave/function, M601/M602;
- mode D250/D251/D230/D231/D232, M667; write WR D320/321,
  read WR D340/341, actual stop-check D240..243 и его WR;
- ручная очередь R2402/R2405/R2406 и actual owner/phase;
- по4 X4/Y4, M613, M713, D263, M1617, M1623, M1627/R2393,
  M1633, M363, R2503/R2513, общий heartbeat;
- разрешение Пуска4 M1533/M1637, задание R2183 и последняя принятая
  ручная частота R2193; различать отсутствие допуска и неисполнение команды;
- M1563 и эквивалентные сохранённые ошибки остальных каналов,
  чтобы текущий D251 не приписать предыдущей операции.

Нужно различить первое падение связи/confirmed/run и последующую ошибку
режимной операции. Последний успешный readback, один скрин или текущий
D251=1/D231=D232=6 не объясняют прошлую остановку4. Не считать суффикс«(2)»
номером ПЧ. Отсутствие собственного Err на приводе не доказывает исправный RTU.

Если обычный trace недостаточен, подготовить **реальный диагностический
native-файл**, сохраняющий первый контекст при отказе/снятии manual RUN
и при ошибке mode worker. Свободную память проверить по actual PLC/HMI/
SCADA, не угадывать адреса. Захват только копирует данные, не меняет управление,
параметры/таймеры, не запускает повтор/Reset. Контекст не стирается следующим
успешным запросом; номер события/причина/насос и raw-слова доступны в текущей
диагностике HMI. Сохранение контекста не должно увеличивать частоту Modbus-посылок.

## 2. Воспроизвести и исправить найденную причину

Использовать actual4 native-пару, изолированный TEST_ONLY/эмуляцию либо
доступное безопасное чтение. Проверить ручную очередь1→2→3→4 и четвёртый
отдельно. При имитации отдельно пометить входы, фактический слой и границы.
Не включать силовой RUN AC590380/220/Err09 ради этого исследования.
На стенде один AC590 без двигателя, на объекте M900G: ошибка неподдержанного
запроса AC590 сама по себе не является причиной полевого отказа M900G.

Воспроизвести успешный mode write/readback, ошибки записи и чтения,
несовпадение/старый ответ, timeout, дополнительную FC03-ошибку при свежей
телеметрии и реальную потерю необходимых данных. Проследить, почему
работающий четвёртый теряет допуск и почему возникает повторная подготовка.

Менять только доказанную причину. **Не отключать аварию/M1627, не удерживать
Y4 при неподтверждённом режиме, не расширять timeout/не вводить бесконечные
повторы и не подменять контрольные признаки одним Q2.** Восстановление связи
не должно самопроизвольно запускать вручную остановленный/заблокированный насос.
Нельзя объявлять штатное снятие RUN ошибкой только потому, что оно мешает тесту.

После правки проверить все4канала, реальную потерю ready/link, окончательное
неподтверждение режима, остальные действующие защиты, арбитраж единственного
Port3 и соответствие ответа тому же адресату/поколению запроса. Сохранить
токи/новые выдержки/SCADA-контракт/BootAck. Native F8 и сохранённый reopen
обязательны для изменённого PLC; Compile и физическая HMI для изменённой HMI.

## 3. Восстановить обратный отсчёт обоих действий

[Полевой дефект/свежие Cloud-проверки](../reports/oshsky-countdown-field-issue-20261126.md).
Требование прежнее: центр верхней строки Main, фактический номер насоса,
«До запуска насоса N: … с» / «До остановки насоса N: … с». Слева бренд,
справа ПЛК/режим; прозрачная подложка, номер/секунды прежним янтарным цветом.
Отсутствие надписи в MANUAL/STOP ожидаемо, но пользователь подтвердил AUTO.

Локализовать конкретный этап при активном ожидании:

1. Прямой экспорт R3120..3125:27402/action1или2/физическая цель/остаток/
   выбранный preset/движущийся heartbeat. Сопоставить R2300/AUTO и реальные
   счётчики/разрешения каскада. R2132 отдельно не заменяет этот контракт.
   Если action=0, выяснить, почему actual PLC не публикует ожидаемый wait,
   включая отмену допуском/подготовкой режима; не дорисовывать таймер в HMI.
2. Actual native Batch CascadeBlock[0..5], CascadeMode и его правильный
   первый элемент после перехода к Batch UInt16/Bytes2. Сохранить исправление
   раскладки r3d; старый public scalar-адаптер не копировать поверх него.
   Сопоставить actual AUTO/packed physical mode, RTC, карту и контракт.
3. LB2110(fresh), LB2111(start), LB2112(stop), LW54010(pump),54011(seconds),
   54012(digits) — либо actual новые адреса, если они менялись. Проверить
   их запись до ранних return и отсутствие перезаписи другими службами/
   новой анимацией. Положительные active/seconds в PLC не считать доказанными
   положительными outputs HMI без чтения.
4. Actual Main-объекты: источники/условия видимости отдельно для пуска и
   остановки, page-local polling новых слов, слои/формат/границы. В r3d
   добавлялись 1×1 RO reads: проверить их на физической панели, а не по имени.

Проверить оба действия для физических номеров1..4, включая цель после
ротации. Подтвердить движение12→11→…→1 и исчезновение после commit,
смену/отмену цели, уход и возврат на Main, смену режима, stale и reconnect.
Один статический кадр/наличие полей настроек не закрывает эти сценарии.
Пределы прежние: пуск до3600с, снятие до1800с; не вводить новые stop-presets.

Если реальный AUTO-каскад сейчас невозможен без силового запуска, использовать
отдельную явно помеченную TEST_ONLY/эмуляцию источника. Проверять тот же
actual путь aliases/допуски/render, не подменять конечные visibility/число
на экране. Отдельно отметить слой имитации и что проверено физической HMI.
Никакого RUN AC590380/220/Err09 или ослабления защит ради таймера.
Полевой выход без TEST_ONLY; в конце actual production STOP-regression.

HMI не пишет PLC-экспорт, не отсчитывает секунды локально, не продлевает
freshness и не задерживает команды/аварийный останов для показа строки.
Если найден тот же root cause, что у токов/старых задержек, подтвердить
устранение **для обоих действий** в новом native-выходе, не объявлять это
автоматически по прошлому fix r3d.

## 4. Анимация и результат

Отсутствие реальных четырёх M900G/нагрузки не блокирует всю работу: завершить
доступный разбор/контролируемое воспроизведение/готовый capture, затем
продолжить анимацию и комплект с явным остатком по полевому эпизоду.

Также выполнить раздел «Восстановить вращение четырёх вентиляторов»
из [того же HMI-задания](oshsky-r3d-physical-panel-local-20261126.md).
Без переноса целого трёхнасосного макроса/конфликта LW, с проверкой реальной
смены кадров, а не одного зелёного значка. После изменения HMI выполнить
необходимый regression уже пройденных пользователем токов/задержек/переходов.

Выдать отдельные сохранённые native-файлы при изменениях, фактический
Desktop-комплект/ZIP и полные Windows-пути/SHA. Не перезаписывать известную
рабочую r3/r3d. PLC не переименовывать «исправленным», если он прежний.
В README различить: причина доказана/исправлена, либо выдан только готовый
захват события и остаётся полевой тест. Во втором случае не заявлять устранение
остановок. Чётко указать, какие файлы предназначены для установки и что сохраняет
полевые параметры. TEST_ONLY и bench data не включать в field-выход.

Приватные native/трассы остаются локально; безопасный diff/проверки/протокол
и HANDOFF передать в handoff-ветку с проверкой remote SHA. Убирать свои
промежуточные окна после сохранения. SCADA r4, Бабанов, другие объекты и общие
службы не менять. Лист выезда27.11 дополнить фактической процедурой захвата,
если без M900G/нагрузки окончательный корень не удалось установить.
