# Довести проверку качества уже работающего штатного графика

05.11.2026 МСК. В `830b298` получена краткая сводка локального результата:
модель сохранена, код импортирован, native Compile All/Save завершены,
импортированная копия активировалась, в Client появились три ряда и обе
физические шкалы, видны архивные данные. Это результат локального CLI,
не новое измерение облака. Пустой Script_49 и отсутствие проекта в каталоге
Server относятся к уже пройденным этапам.

Не повторять Save As/импорт/создание переменных/перекомпиляцию того же кода,
не возвращать рабочий график к скелету и не перезапускать транспорт/сборщик.
Точные текущие пути/SHA и подготовленный producer взять из своих приватных
артефактов. Подробный HANDOFF, отклонённый за приватные сведения, не публиковать
повторно другим способом: этот проход передавать краткой сводкой и отдельно
проверенными исходниками/тестами без частных конфигураций/путей/журналов.

Остался один направленный проход:

1. Прочитать фактический код producer/таймера из сохранённой проверенной
   копии. Установить, что каждый ряд получает свои данные только по чтению,
   преобразует raw один раз, а цели — именно внутренние переменные
   представления. Исходные OPC/command-переменные и исторические raw-ряды
   сохраняются. Не делать вывод о корректности по имени переменной или
   одной точке курсора.
2. Проверить PV: GOOD у значения и признака источника, SourceOK=1,
   согласованная карта и живой прогресс счётчика ПЛК. При SourceOK=0/BAD
   или устаревании — недоступность/разрыв, без начального нуля, ложного
   продолжения или соединения разрыва после восстановления. Подтверждённый
   ноль остаётся допустимым измерением. При недостоверности одного PV
   другие самостоятельно достоверные ряды не исчезают.
3. Проверить эту логику на изолированных внутренних тестовых входах/адаптере
   в отдельной копии: valid → invalid → valid, stale → fresh, и исходный
   ноль. Рабочие источники ПЛК/OPC и калибратор программно не менять.
   Для скриптовой логики использовать синтетические проверки; отдельно
   показать, как фактически отображает/сохраняет пропуск native-архив.
   Тестовое представление явно пометить; не выдавать его данные за показания
   стенда. Не выдумывать setter качества или поддержку NaN. Если native
   хранит последнюю точку как достоверную, это дефект, который нужно
   воспроизвести и исправить с проверенным source, либо точно назвать
   ограничение до приёмки качества.
4. Прочитать фактическую настройку периода таймера и интервал архивации.
   При необходимости измерить несколько последовательных срабатываний
   счётчиком только во внутренней диагностике. Архив «по изменению»/
   «комбинированный» не обязан давать точку на каждом тике: метки архивных
   записей не доказывают точный период таймера. Сравнить прежнее/новое
   сохранение отдельно от частоты выполнения скрипта. Не вводить новую
   команду оборудованию для получения изменяющегося ряда.
5. Проверить переходы 1/6/24 ч в правильную существующую группу текущего
   Client, общую шкалу PV/SP в барах, отдельную частоту в герцах, один знак,
   легенду/курсор/возврат. Нулевая частота может совпадать с осью; проверить
   её видимость цветом/легендой и включение ряда. Отображение нуля в SCADA
   само не является независимым измерением физической частоты ПЧ.
   Проверка ненулевой физической частоты остаётся отдельным стендовым опытом,
   не поводом тормозить доступный разбор кода/качества.

Если требуется исправление — отдельная копия и воспроизводимый source,
нужные тесты, затем native Compile/Save и повтор затронутого случая.
Если исправлений нет, не повторять общий rebuild/47 облачных групп ради
документации. Не нажимать Apply/пуск/сброс ради UI; не очищать БД/архивы.
Подробные доказательства сохранять локально; в публичную ветку только
согласованную краткую сводку и проверенный обезличенный код/тесты. main
не менять, чужие местные изменения сохранить.

По окончании явно разделить: видимые три ряда/архив подтверждены; качество,
свежесть, пропуски и переходы проверены либо имеют конкретный остаток.
Следующая реализация интерфейса — рабочая форма «Настройки» по согласованному
макету; нынешний информационный каталог не считать готовой формой.
