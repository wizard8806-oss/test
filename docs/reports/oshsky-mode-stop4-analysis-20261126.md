# Ошский: повторная остановка ПЧ4 и подготовка режима, 26.11.2026

## Новые полевые сведения пользователя

Пользователь уточнил: «ошибка подготовки режимов ПЧ» регулярно появлялась
и сопровождалась остановкой ПЧ4 **в ручном режиме, уже во время работы**.
На самом ПЧ4 собственного кода аварии не было, привод просто останавливался.
Задание c671d12 локальному ещё не передано. Первичная физическая проверка
токов/задержек/переходов пройдена, эта авария ею не закрыта.

Это согласуется со снятием команды PLC, но фактические Y4/слово управления
в момент события не записаны. Нельзя объявлять внутреннюю неисправность ПЧ,
точную ошибку RS485 или ошибку ПЛК установленной по одной этой корреляции.

## Что установлено по программе

Исходник04 SHA
`a25f9b5d2fe006bcb039896bae3989569b08e1b1adc4b503a755bfd5e3b22993`.
Из него прежними source-locked builders воспроизведена generated r3
(SHA `08d153b92fa0fa47e5c9ca0e568c6e0f7cf98f71faef634d88e56828a96cf820`).
Это временная Cloud-копия, не Windows-native файл из полевого комплекта.
Для первого опыта 28 выбранных сетей управления/аварии совпали с04.
Локальный [разбор точной дисковой r3](oshsky-first-start-r3-readonly-local-20261126.md)
ранее подтверждал тот же узел режима; установленная полевая программа не считана.

Использованы существующие bounded bytecode interpreters из
`validate_three_pump_pdw_candidate.py` с декодером M/T/X/Y из
`validate_drive_reset_r15.py`. Ни FUN150, ни физический порт, ни реальная
периодичность таймеров не моделировались. Все ниже — проверки отдельных
связанных предикатов, не воспроизведение полного полевого события.

### 1. Ошибка mode worker снимает команду выбранного насоса

Четыре опыта, выбранный канал1/2/3/4. Введён M667=1 при ручном mode-job
для этого target, остальные разрешения исходно исправны. Actual сети
65.M101..115, run permit/drop и90.02..05 дали:

| Target | Защёлка | Код ПЛК | Результат Y1/Y2/Y3/Y4 |
| --- | --- | --- | --- |
|1|M1624|R2390=100|0/1/1/1|
|2|M1625|R2391=100|1/0/1/1|
|3|M1626|R2392=100|1/1/0/1|
|4|M1627|R2393=100|1/1/1/0|

Во всех четырёх опытах M1563=1. Для4: 65.M113..115 сохраняют ошибку,
65.M182 закрывает M1633, 65.M185 снимает M363,90.05 отключает Y4.
Это проверенный предусмотренный путь блокировки, **не доказательство,
почему возник M667 на объекте**. Код100 — код контроллера, не native Err ПЧ.

### 2. Есть более ранний путь от обычного FC03 к остановке

В ручном работающем канале введён результат ошибки обычного FC03 для того
же slave. Проверены дополнительные строки0-based1/4/6 для1/2/3 и7/14/15
для4 — всего6опытов. Для ПЧ4 это строки8/15/16 в интерфейсе с нумерацией от1;
его собственная семисловная телеметрия — строка18 (0-based17).

Обработчик normal poll сбрасывает M613 по ошибке slave4/FC03 без различения
строки. Затем65.62 сбрасывает M713, SourceReady4/M1617 становится ложным,
M1633/M363 и Y4 отключаются. При ещё свежем собственном снимке R2513 остаётся2.
Одинаковый механизм получен для всех6опытов, включая три дополнительные
строки ПЧ4. Фактический номер строки специально не определяет generic-link reset.

Важное ограничение: этот второй опыт проверяет снятие RUN при введённой
ошибке опроса. Он **не проверял** полный последующий цикл очереди и появление
общей аварии подготовки. Полевой сбой может начинаться с иной причины.
Нельзя автоматически заменить контрольный permit свежим Q, убрать защиту
или объявить любой FC03 harmless. Нужно поймать первый сбой до очистки контекста.

## Что осталось неизвестным

- Какой запрос/строка/результат возник первым: normal poll, запись режима,
  readback, stop-check или deadline/потеря ready.
- Что было раньше: M613/M713/Y4 упали, либо mode worker уже ошибся.
- Совпадает ли полевая программа с exact r3 и почему симптом чаще у4.
- Был ли физически снят Y4, либо изменилось слово управления/другой сигнал.

Срез стенда из [локального протокола](oshsky-live-bench-20261126.md)
D251=1/D231=D232=6 с успешными WR относится к более поздней операции другого
контекста, не к неудачной работе ПЧ4. Он не закрывает этот вопрос.

Следующее [объединённое задание](../tasks/oshsky-mode-stop4-and-animation-local-20261126.md)
ставит остановку ПЧ4 выше анимации. Нужна воспроизводимая причина и исправление;
если полевой сбой не воспроизведён — готовый диагностический захват первого
события в отдельной native-копии, с честным статусом «причина ещё не установлена».
